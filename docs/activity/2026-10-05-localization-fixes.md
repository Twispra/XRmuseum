# 2026-10-05 本地化校验器误报修复（回应 Issue #16）

分支 `codex/localization-2026-10-05`（PR #13）。

## 问题

`LocalizationValidation.cs` 的缺字检查在文案之外**硬编码了一段探针字符串**：

```csharp
probe.Append("[[ ]]。，、");
```

其中**顿号 `、`（U+3001）**既不在已保存的字体图集里，当前文案与固定按钮标签也都不使用它。
于是在已保存资产上运行 `RunBatch` 会报一条**假失败**：

```text
字体缺少 1 个字形：'、'(U+3001)
```

10 项通过、1 项失败、退出码 1 —— 但这并不是真实的中文展示缺字。

## 修法：按实际渲染字符集合校验

不再硬编码任何标点，探针改为**由实际会被绘制的字符构成**，来源三类：

1. 文案表里每条的中文与英文 —— 运行时会原样显示；
2. 缺 key 时显示的 `[[key]]` 标记 —— 标记里的 key 本身也会被画出来；
3. 语言按钮上那两个固定标签（走 `NativeName()`，不经过文案表，最容易漏配字体）。

**缺字检测能力没有被削弱**：它仍然逐字符核对实际要渲染的文本，真实缺字照样会被报出来。

同时把失败信息里的分隔符从顿号换成逗号，避免读者误以为问题没改干净。

## 字符清单与字体对齐

`Fonts/make-charlist.py` 之前会在文案之外追加 `<`、`>` 和 en dash `–`，
导致「清单 193 个字符 / 字体 190 个字形」这种看起来自相矛盾的状态。
现在清单只收**真正会被绘制**的字符，与校验器口径一致：

- 移除 `<` `>` —— TMP 富文本标签的分隔符，标签会被解析掉、不绘制；
- 移除 en dash `–` —— 文档与生成源都不需要它（保留 em dash `—` 与下划线 `_`，TMP 内部会用到）。

## 验证（离线复刻校验器逻辑）

**本轮未在 Unity 里运行**（修复者侧无法驱动编辑器图形界面），改为精确复刻校验器的判断逻辑：
按上面的规则从 `LocalizationTable.asset` 取出全部文案的中英文与 key，加上 `[]`、`中文`、`English`，
再与已知的字体字形集合求差。

```text
修复后的探针（= 实际渲染字符集合）
  缺字: 无          -> RunBatch 应全部通过、退出码 0

对照：修复前的旧探针（含硬编码的 [[ ]]。，、）
  缺字: '、'(U+3001)  -> 与 Issue #16 报告的结果一致
```

**对照那一行是关键证据**：它说明「缺字检测」这条路径本身有效 ——
正是它抓到了旧探针多要求的那个顿号。修复只去掉了不该被要求的那一个字符。

## 需要复审者执行的验收

离线核对不能代替真实运行，请在 Unity 2022.3.62f3c1 / Windows 上：

1. 对**已保存资产**（不跑 Create / Setup，不重新生成任何东西）运行
   `Museum.Localization.EditorTools.LocalizationValidation.RunBatch`；
2. 确认**全部检查通过且进程退出码为 0**。

## 限制

- 未在真实 Headset 上验证中文可读性；未做无障碍或参与者评价；未在 PQ604A/B/C 构建。
- 本轮只改校验器与字符清单，**未改动任何已保存的字体资产、文案表或主场景**。
- 若要新增字体里没有的标点（例如顿号），正确做法是把它加进字符清单并**重烤一次字体**。
