# Phase 3 评价方案（可访问性专项）

本目录是 Phase 3「评价 → 改进」闭环的**评价工具与记录**，服务于课程
*Phase 3 Assessment Rubric*（Canvas 文件 `COMP5424-Group-Project-Assessment-Rubric-P3-202627A.pdf`；
课程原件不纳入本仓库）的组内 3+2 分与个人 1 分。

> 定位：这是**形成性（formative）专家走查 + 试点可用性测试**，不是最终用户研究。
> 参与者以组内成员与同学为主，样本小、非随机，结论只用于本轮改进优先级，
> **不外推为"目标访客已验证"**。凡未实际执行的环节，本目录一律标注"未执行"。

## 1. 为什么评这些（评价问题）

Scenario B 是 *Accessible Museum Experience*，可访问性是本场景的**重要需求**而非附加项；
`docs/course-requirements.md` 也把"可访问性/舒适性"列为持续适用要求。
2026-10-11 合入的[无障碍与舒适性走查](../accessibility.zh-CN.md)已经用脚本量出三个**可检验的具体假设**，
本方案把它们转成可观察的评价问题：

| 编号 | 评价问题 | 来源（已有证据） | 观察什么 |
| --- | --- | --- | --- |
| EQ1 | 坐姿、实际观看距离下，访客能否**读懂**说明面板与展签？ | 21 个 TMP 组件 `fontSizeMin ≤ 0.05`（20 个是 0.02），最大压缩比 72.5× | 是否凑近、是否眯眼、是否放弃阅读、是否读错 |
| EQ2 | 不依赖颜色，能否分辨热点**可选 / 悬停 / 已访问**？ | 三态仅换色 `#1FCCE6`/`#FFAD26`/`#40F280`，两态带透明度 | 是否知道"这个点过了没有"、是否重复点已访问项 |
| EQ3 | 说明面板 30 秒后淡出，是否**打断阅读**？淡出后能否自己找回？ | `explanationHoldSeconds=30`、`explanationFadeSeconds=1`，重选可重启 | 读到一半被打断时的反应、能否自行复现 |
| EQ4 | 三语切换是否**可发现**？术语是否易懂？ | 语言入口在场景 (2.6, 0, 6.2)，距起点 5–6 m | 是否找到入口、是否在错的时机找、术语误解 |
| EQ5 | 访客能否**自主复位**并知道下一步该做什么？ | `hasConfiguredHome` + 独立复位脚本已存在 | 是否卡住、是否需要主持人提示、是否知道"我逛完了" |

## 2. 方法

### 2.1 两个层次（按成本递增，可只做第一层）

**层次 A：专家启发式走查（expert heuristic walkthrough，无需外部参与者）**

- 2–3 名组员各自按 [任务清单](task-list.zh-CN.md) 走一遍保存的 `MuseumStart`，
  对照 EQ1–EQ5 逐项判定，并用 Nielsen 0–4 严重度打分（见[观察与编码](observation-and-coding.zh-CN.md)）。
- 产出：每人的独立观察表（署名）+ 合并后的 issue log（按严重度排序）。
- 诚实边界：这是**专家评审**，不是用户测试；写报告时必须如实称其为 expert review。

**层次 B：试点 think-aloud（3–5 名非项目组参与者）**

- 单人 45–60 分钟，边说边做；主持人只按[脚本](moderator-script.zh-CN.md)提示，不代操作。
- 产出：录音/笔记转写的匿名摘录 + 观察表 + 编码结果。
- 每场前后各 5 分钟用于知情同意与收尾访谈。

### 2.2 参与者与选择理由（评分项"participant selection is justified"）

| 层次 | 人数 | 纳入标准 | 理由 |
| --- | --- | --- | --- |
| A | 2–3 | 组内成员，未参与该功能开发者优先 | 成本最低、可在无头显环境下用截图与资产数据完成；用于**先筛掉明显问题**，避免浪费真人时段 |
| B | 3–5 | 非项目组、有/无 VR 经验各半、视力正常或矫正后正常 | 小样本定性研究以**覆盖多样性**而非统计代表性为目标；明确记录 VR 经验与是否戴眼镜 |

**必须写进报告的局限**：样本小、便利抽样、组内成员参与 A 层、单次会话、跨设备一致性未控。
不得据此外推为"目标访客群体已验证"。

## 3. 一场 60 分钟怎么跑

| 时间 | 环节 | 要点 |
| --- | --- | --- |
| 0–5 | 知情同意 | 读[同意书](consent-and-information.md)，口头确认，强调可随时退出、不评价个人 |
| 5–10 | 设备与安全 | 头显佩戴、瞳距、坐姿就位；告知**任何不适立即说停**并摘下头显 |
| 10–15 | 热身 | 让参与者自由看 1 分钟，建立发声习惯（"你在看什么、想做什么"） |
| 15–45 | 5 个任务 | 按[任务清单](task-list.zh-CN.md)，每任务 5–6 分钟；卡住超过 90 秒给一级提示 |
| 45–55 | 半结构化访谈 | 按脚本收尾问题；重点问"哪里让你犹豫/放弃" |
| 55–60 | 收尾 | 致谢、说明数据用途与匿名方式、确认可否引用摘录 |

**安全与退出**：出现头晕、恶心、眼疲劳立即停止；提供座位与休息；不在参与者疲劳时继续。
**数据最小化**：只保留任务相关的屏幕录像/音频与笔记；不采集姓名、学号、联系方式；
转写时用 P1/P2 代号替换，删除可识别信息；原始文件只存项目组受控位置，**不进 Git**。

## 4. 从证据到改进（评分项"evidence-to-action"）

```
观察表/转写 → 编码（EQ1–EQ5 + 归纳新码） → issue log（含严重度） → 优先级排序 → 实施 → 前后对比 + 回归
```

**优先级公式（写进报告，便于复核）**：
`优先级 = 严重度 × 影响人数占比 ÷ 实施成本`，同分时按"是否阻断核心流程"排前。
每条 issue 必须写：来源证据编号、受影响需求（EQ 编号）、严重度、成本估计、决定（实施/延后/不处理+理由）。

**改进验证要求**：每项实施的改动都要有**改前/改后**证据（截图、脚本读数、验证器报告），
并跑一次**受影响行为的回归**（不只看新功能）。
